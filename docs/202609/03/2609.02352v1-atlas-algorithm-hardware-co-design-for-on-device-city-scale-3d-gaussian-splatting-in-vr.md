## 摘要
3D高斯泼溅（3DGS）近来在建筑学界引起了广泛关注。然而，在移动VR设备上实现城市规模的3DGS仍然具有挑战性，因为大规模场景的内存需求远超当今移动GPU的内存容量。本文提出Atlas，一种设备端城市规模3DGS渲染框架，能够在无需运行时互联网接入的情况下实现可扩展渲染。关键洞察在于，尽管完整的3DGS模型非常庞大，但每一帧在当前姿态和细节层级要求下仅需要一小部分高斯子集。基于这一洞察，Atlas引入了一种分层内存卸载机制，仅将必要的高斯数据动态加载到设备内存中。为了进一步提升性能，Atlas提出了时间感知的LOD搜索和立体光栅化，以避免VR中的冗余计算。我们进一步表明，我们的技术可以与现有3DGS加速器集成，且硬件开销可忽略不计。总体而言，与GPU基线相比，Atlas实现了18.5倍的加速，与最先进的3DGS加速器相比实现了3.9倍的加速，同时节能92.4%。

## Abstract
3D Gaussian splatting (3DGS) has drawn significant attention in the architectural community recently. However, enabling city scale 3DGS on mobile VR devices remains challenging, as the memory requirement of large scale scenes far exceeds the memory capacity of today's mobile GPUs. This paper presents Atlas, an on device city scale 3DGS rendering framework that enables scalable rendering without runtime Internet access. The key insight is that although the full 3DGS model is massive, each frame only requires a small subset of Gaussians under the current pose and level of detail requirement. Based on this insight, Atlas introduces a hierarchical memory offloading mechanism that dynamically loads only necessary Gaussian data into device memory. To further improve performance, Atlas proposes temporal aware LoD search and stereo rasterization to avoid redundant computation in VR. We further show that our technique can be integrated with existing 3DGS accelerators with negligible hardware overhead. Overall, Atlas achieves 18.5x speedup over the GPU baseline and 3.9x speedup over the state of the art 3DGS accelerators, with 92.4% energy savings.

### 2. 论文提出的方法论

#### 核心洞察
- 城市规模3DGS模型虽然极其庞大，但**实际渲染每一帧时，仅需要当前相机姿态和LoD阈值之下的一小部分高斯子集**。
- 内存需求具有**阶段差异性**：初期LoD搜索阶段需要访问大量高斯数据，但搜索结果确定后，活动高斯数量急剧下降至移动设备可承载的规模。
- LoD搜索结果展现出极强的**帧间时间相似性**（相邻帧重叠率超过99%）以及**立体视觉中左右视图的强相似性**（非重叠像素不足1%）。

#### 框架总览（Atlas）
Atlas由四个主要层次组成：**LoD树遍历 / 搜索（Sec. 5）**、**运行时高斯管理（Sec. 6）**、**立体光栅化（Sec. 7）**以及**硬件架构支撑（Sec. 8）**。

#### 关键技术细节

**(1) 分层内存卸载与数据管理**
- 将城市场景划分为**小型空间块（spatial blocks）**，在运行时仅按需激活视点附近的块，其余块存储在CPU内存/磁盘等低级存储中。
- 每个块内的高斯数据进一步分为两类：
  - **轻量LoD元数据**（如位置、尺度、树连接性），用于LoD搜索，常驻GPU内存；
  - **存储密集的渲染属性**（如球谐函数系数等），仅当高斯被选入"cut"后按需加载。
- 设计了异步的**运行时高斯管理系统**：维护运行时高斯表（记录驻留状态与重用窗口），按需加载缺失属性，并通过回收窗口机制（阈值设为32帧）驱逐不再需要的高斯，保持GPU内存占用紧凑。

**(2) 时间感知的LoD搜索**
- 离线阶段将块内LoD树划分为多个近似等大小的子树以保证GPU负载均衡。
- **原始帧**采用"完全流式LoD树遍历"：利用BFS顺序进行遍历调度，以GPU共享内存流式访问树节点，避免不规则内存访问。
- **后续帧**采用"时间感知LoD搜索"：只搜索包含上一帧cut结果的子树，避免对整个LoD树进行重复遍历；当搜索无法形成完整cut时，回退到父级或相邻子树继续搜索。该方法产生的cut结果与完整遍历位精确一致。
- 文中未给出复杂公式，渲染阶段沿用经典3DGS的颜色混合公式：C(p)=Σ Γᵢ αᵢ cᵢ，其中Γᵢ为累计透射率。

**(3) 立体光栅化（Stereo Rasterization）**
- 利用**三角测量原理**计算视差 X = Bf / D（B为双眼基线距离，D为高斯深度），从而将左眼图像中通过α检查的高斯直接映射到右眼图像中对应的瓦片位置。
- **预处理与排序**：通过在双眼后方放置虚拟相机获得共同视场，使用更宽的视场角一次完成预处理和排序，供双眼共享。
- **右眼光栅化**：根据最大视差（典型VR设置下约16像素），高斯只会落在当前瓦片右侧0到3个瓦片范围内。右眼某瓦片的相交高斯通过合并四个预排序列表获得，无需重新排序——类似归并排序的合并阶段。
- 该流程与原有管线逐位精确（bit-accurate），不损害图像质量。

**(4) 架构支持**
- 以GSCore为基础架构，在核心中添加少量硬件单元：
  - **立体重投影单元（SRU）**：将左眼透过α检查的高斯重投影到右眼视点；
  - **立体缓冲（stereo buffer）**：采用行缓冲设计，每行存储一种视差类别，避免存储冲突；
  - **合并单元**：读取四行头部，合并得到右眼瓦片的完整有序高斯列表。
- 通过让右眼直接消费缓冲的高斯数据，避免了重复的缓冲区内存访问，实现左右眼流水线的细粒度重叠。

### 6. 主要结论与发现

- Atlas在移动GPU基线上取得**18.5倍**加速（运动到光子延迟），相对现有SOTA 3DGS加速器（GSCore）取得**3.9倍**加速。

- 运行时高斯管理降低GPU显存需求最高达**7.0倍**，使所有大规模场景的显存低于12GB——满足主流移动VR设备限制。
- 时间感知LoD搜索实现最高**8.1倍**加速，相比传统LoD搜索方法提升显著。
- 立体光栅化在GPU、GBU和GSCore上分别带来1.4×、1.7×和1.9倍的本地渲染（预处理+排序+光栅化）加速。
- 渲染质量几乎无损（PSNR损失约0.1dB，SSIM无损失），因为其立体光栅化是逐位精确的，损失仅来源于按需加载和LoD搜索频率。
- Atlas可与现有3DGS加速器架构集成，硬件面积开销可控（相对GSCore约增加14%）。

### 8. 不足与局限

- **对“帧间隔w=4”带来的视觉一致性失真缺乏主观评价**：LoD只每4帧搜索一次，虽然论文说明视觉不一致性尚可容忍，但并未提供主观实验或量化帧间闪烁程度。
- **感知质量评估不足**：评价仅基于PSNR/SSIM这类全参考图像质量指标，缺乏用户研究来评估真实VR体验（延时感、晕动、空间真实感）。
- **90FPS达标依赖硬件放大**：基准配置下约为70.9FPS；达到90FPS需要通过将渲染单元从128翻倍到256，增加62.9%面积——论文没有分析该扩展对功耗的连带影响，而其标题和摘要避开了“实时”声明中的含糊处。
- **硬件仿真的进一步假设**：虽然做了RTL级评估，但最终性能估计依赖一个延迟和功耗参数化自GPU测量与RTL综合结果的模拟器校准。这些参数与实际SoC集成后的总线/缓存行为可能存在差异。
- **训练成本完全未提及**：对标大规模3DGS训练数据的生成（HierGS、OctreeGS、CityGS之类）也许是一次性/离线的，但它的训练成本并没有被纳入端到端效率评估，对于完整的流程公平性评估仍然是一个缺口。
- **场景类型有限**：虽然覆盖了城市级航空与街道视角，但没有验证动态场景、变化光照等复杂情况下的鲁棒性——3DGS本身多用于静态重建，但在VR应用中用户操作偶尔会触碰动态物体（门、人等），该类约束尚不明朗。
- **立体光栅化在不同头部旋转方向下的鲁棒性有限**：论文视差推导基本假设相机间水平基线排列（common stereo setup），若未来设备采用特殊光学结构或用户头部产生显著的俯仰/翻滚旋转，此方法需要加以推广才能保持位精确性，论文中并未讨论到这种边界情况细节。
- **对“低级存储层”吞吐量假设**：设计高度依赖磁盘/CPU内存读取速度，对移动用户的存储介质差异（不同规格UFS/eMMC/SSD）并没有建模或限制，潜在影响性能普适性的推断还属于比较开放的层面。
